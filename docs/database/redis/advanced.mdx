# Redis 进阶指南

当应用规模不断扩大，Redis 不再仅仅是单机的一层缓存，而是整个分布式架构中的核心枢纽。本文将深入讲解 Redis 的持久化原理、高可用架构、内存淘汰机制以及常见缓存问题的解决方案。

## 1. 持久化原理剖析

为了防止服务器宕机导致内存数据丢失，Redis 提供了 RDB 和 AOF 两种持久化机制。

### RDB (Redis Database)

RDB 会定期保存当前时间点内存数据的全量快照（如 `dump.rdb` 文件）。

- **执行过程**：Redis 会 `fork()` 出一个子进程，利用操作系统的 **COW (Copy-On-Write) 写时复制** 技术，子进程将此时的内存状态写入磁盘。主进程继续处理客户端请求，不受阻塞。
- **触发机制**：可通过 `save 60 1000` 配置（60秒内有 1000 次修改触发 `bgsave`），也可手动执行 `BGSAVE`。
- **优缺点**：恢复速度极快，文件紧凑；但最后一次快照后的数据在宕机时会丢失。

### AOF (Append Only File)

AOF 记录每一次写命令，重启时通过重新执行这些命令来恢复数据。

- **刷盘策略 (`appendfsync`)**：
  - `always`：每次写都刷盘，极慢但最安全。
  - `everysec`：每秒刷盘一次，默认选项，性能与安全的良好折中。
  - `no`：交由操作系统决定。
- **AOF 重写机制 (Rewrite)**：随着命令不断追加，AOF 文件会越来越大。Redis 会触发 AOF 重写（也是通过子进程），将多条对同一个键的修改命令压缩合并为一条（例如把多条 `INCR` 变更为直接 `SET` 最新值），以减小文件体积。

### 混合持久化

Redis 4.0 引入了 RDB-AOF 混合持久化机制。在 AOF 重写时，将当前的内存状态以 RDB 格式写入文件头部，随后的增量写操作以 AOF 格式追加。它结合了 RDB 恢复快和 AOF 数据丢失少的双重优点。

## 2. 主从复制与哨兵模式 (Sentinel)

为了提高读性能并提供数据冗余，需要搭建主从架构；为了实现故障自动转移，需要引入哨兵。

### 主从复制

主节点负责处理写请求，从节点复制主节点的数据并处理读请求。

- **全量同步**：当从节点首次连接主节点时，主节点执行 `BGSAVE` 生成 RDB 文件并发送给从节点，从节点清空旧数据并载入 RDB。
- **增量同步**：在网络断开重连时，如果偏移量（offset）在主节点的积压缓冲区内，主节点仅发送断线期间的写命令。
- **配置**：在从节点执行 `REPLICAOF <masterip> <masterport>`。

### 哨兵模式 (Sentinel)

哨兵是一个独立的进程，负责监控主从集群。

- **监控与判定**：哨兵定期向节点发送 PING。若节点未回复，哨兵会将其标记为**主观下线**；若多数哨兵都认为主节点下线，则标记为**客观下线**。
- **故障切换 (Failover)**：当主库客观下线后，哨兵集群会进行选举，挑选出一个数据最新的从库，将其提升为新的主库，并通知客户端及其他从库更新配置。

## 3. 集群模式 (Redis Cluster)

当单台机器的内存或并发写能力无法满足需求时，必须采用分片架构：Redis Cluster。

### 架构与槽位分配

- Redis Cluster 没有中心节点，采用无中心架构。
- 整个集群被划分为 **16384 个哈希槽 (Hash Slot)**。
- 当客户端操作某个键时，Redis 会计算 `CRC16(key) % 16384` 得到槽位编号。
- 每个主节点负责一部分槽位。例如，节点 A 负责 0-5000，节点 B 负责 5001-10000。

### 请求路由与数据迁移

- **Gossip 协议**：节点之间通过 Gossip 协议不断交换状态信息。
- 当客户端发送请求到错误的节点时，该节点会返回一个 `MOVED` 错误，告诉客户端正确的节点 IP 和端口，客户端随后进行重定向。
- 扩容时，可在线将部分槽位从旧节点平滑迁移到新节点。

## 4. 内存管理与淘汰策略

Redis 的内存不是无限的，必须合理配置上限和淘汰策略。

### maxmemory 配置

在 `redis.conf` 中设置 `maxmemory <bytes>` 限制 Redis 能使用的最大内存。

### 内存淘汰策略 (Eviction Policies)

当内存达到限制时，Redis 会根据配置触发淘汰：

- `noeviction`：默认策略，不淘汰数据，只接受读请求，拒绝写请求并报错。
- `allkeys-lru`：在所有键中，使用近似 LRU（最近最少使用）算法淘汰不常用的键。（最常用的缓存策略）
- `volatile-lru`：仅在设置了过期时间的键中，淘汰最近最少使用的键。
- `allkeys-lfu` / `volatile-lfu`：Redis 4.0 引入，基于 LFU（最不经常使用频率）算法淘汰。

## 5. 分布式锁实战

在分布式系统中，需要一种跨进程的机制来防止多台服务器同时修改同一资源。

### 基本实现

基于 `SET` 命令的 `NX`（Not Exists，不存在才设置）和 `EX`（Expire，过期时间）选项：

```redis
# 尝试获取锁，设置 10 秒超时防止死锁
SET resource_lock "unique_request_id" NX EX 10
```

释放锁时必须确保**只能释放自己加的锁**，这通常需要使用 Lua 脚本保证原子性判断和删除操作。

### 锁续期 (Watchdog)

如果业务执行时间超过了锁的过期时间，锁会被自动释放，导致并发问题。流行的客户端（如 Redisson）实现了“看门狗”机制：后台线程定期检查业务是否仍在执行，如果在执行，则自动延长锁的过期时间。

## 6. 高级数据结构

除了五大基础结构，Redis 还提供了特殊场景的利器：

- **Bitmap (位图)**：底层仍是 String。利用 bit 存布尔值，极其节省空间。常用于实现百万用户的每日签到记录或活跃统计。
- **HyperLogLog**：用极小的空间（约12KB）进行基数统计（去重估算）。常用于统计海量 UV（独立访客）。
- **GEO**：支持经纬度坐标的存储与查询（如搜索“附近的司机”）。
- **Stream**：Redis 5.0 引入的专业消息队列数据结构，支持消费者组机制。

## 7. 缓存高频经典问题

### 缓存穿透 (Cache Penetration)

- **问题**：客户端频繁查询缓存中和数据库中都**根本不存在**的数据（通常是恶意攻击），请求全部落到数据库。
- **解决**：对查询不到的结果也缓存（设为 NULL 并带短暂过期时间）；使用 **布隆过滤器 (Bloom Filter)** 提前拦截不存在的键。

### 缓存击穿 (Cache Breakdown)

- **问题**：一个**极度热点**的键在失效的瞬间，大量并发请求发现缓存未命中，全部同时去数据库加载数据，压垮数据库。
- **解决**：使用互斥锁（如分布式锁），只允许一个线程去数据库查并更新缓存，其他线程等待；或者对核心热点数据设置“永不过期”（通过后台任务异步更新）。

### 缓存雪崩 (Cache Avalanche)

- **问题**：大量缓存数据在**同一时间点过期失效**，或者 Redis 集群大面积宕机，导致海量请求直接冲垮数据库。
- **解决**：过期时间加上一个随机值，打散失效时间；提前建立 Redis 高可用集群预防宕机；应用层开启限流与降级策略。
