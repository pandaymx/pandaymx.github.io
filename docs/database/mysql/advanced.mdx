# MySQL 进阶指南

本文档针对需要处理高并发、海量数据和复杂架构的中高级开发者及 DBA，深入剖析 MySQL 核心组件原理及优化策略。

## 1. InnoDB 存储引擎

InnoDB 是 MySQL 的默认和最核心的存储引擎，提供了完备的事务支持和高可靠性。

### InnoDB vs MyISAM

- **InnoDB**：支持事务（ACID）、支持行级锁、支持外键，灾难恢复能力强。现代应用的首选。
- **MyISAM**：不支持事务，只支持表级锁，但在只读或很少更新的场景下查询速度极快，如今较少使用。

### InnoDB 核心架构

- **Buffer Pool (缓冲池)**：缓存磁盘上的数据页和索引页，极大提高读取性能。修改数据时先修改 Buffer Pool，然后定期刷脏到磁盘。
- **Redo Log (重做日志)**：记录物理修改。为了保证事务持久性（Durability），即使系统崩溃，重启后也能通过 Redo Log 恢复已提交的事务（WAL 机制，Write-Ahead Logging）。
- **Undo Log (回滚日志)**：记录数据的历史版本。用于事务回滚和实现 MVCC。

### MVCC 与行级锁

- **MVCC (多版本并发控制)**：InnoDB 通过每一行隐藏的回滚指针和 Undo Log 构建版本链，再结合 **Read View (读视图)** 来实现快照读，从而避免读写冲突。
- **事务隔离级别**：InnoDB 默认隔离级别为 **Repeatable Read (可重复读)**，并且利用 Next-Key Lock 机制在很大程度上解决了幻读问题。

## 2. 查询优化与 EXPLAIN

分析慢查询是后端开发者的必备技能。

### EXPLAIN 输出详解

使用 `EXPLAIN SELECT ...` 可以查看优化器的执行计划。关键列说明：

- **type**：连接类型，反映查询效率。最好到最差依次是：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`（全表扫描）。
- **key**：实际使用的索引。如果为 NULL 说明没用上索引。
- **rows**：MySQL 预估需要读取的行数。
- **Extra**：包含额外信息。常见的有 `Using index`（使用了覆盖索引，极好）、`Using where`、`Using filesort`（需要额外排序，尽量避免）、`Using temporary`（使用了临时表，极耗性能）。

### 慢查询日志分析

开启 `slow_query_log` 可以记录执行时间超过阈值的 SQL：

```ini
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1  # 记录超过 1 秒的查询
```

可配合 `mysqldumpslow` 工具分析日志文件。

## 3. SQL 优化技巧

- **避免全表扫描**：在 `WHERE` 和 `ORDER BY` 涉及的列上建立合适的索引。
- **JOIN 优化**：尽量遵循“小表驱动大表”的原则。参与 JOIN 的被驱动表的关联字段必须有索引。
- **深度分页优化**：对于 `LIMIT 1000000, 10` 这种查询，MySQL 会扫描 1000010 行再丢弃前一百万行。优化方案：
  - **延迟关联**：先通过覆盖索引查出对应页的 ID，再用这些 ID 回表查询详情：
    ```sql
    SELECT * FROM users INNER JOIN (SELECT id FROM users ORDER BY id LIMIT 1000000, 10) AS tmp USING(id);
    ```
- **COUNT(\*) 优化**：在 InnoDB 中 `COUNT(*)` 会进行全表扫描。如不需要精准数字，考虑使用近似值，或者将总数维护在单独的计数表或 Redis 中。
- **GROUP BY 优化**：`GROUP BY` 默认会排序，如果没有排序需求，可以加上 `ORDER BY NULL` 避免多余的排序开销。

## 4. 主从复制与集群

随着业务量增长，单节点 MySQL 无法支撑，必须引入主从架构。

### 主从复制原理

1. 主库将数据更改记录到二进制日志 (**Binlog**)。
2. 从库的 IO 线程连接主库，拉取 Binlog 并写入本地的 **Relay Log (中继日志)**。
3. 从库的 SQL 线程读取 Relay Log 并重放执行，完成数据同步。

### 复制模式演进

- **异步复制**：主库不等待从库响应。性能好但主库宕机可能丢数据。
- **半同步复制 (Semi-sync)**：主库等待至少一个从库接收并写入 Relay Log 才返回成功，兼顾性能和数据安全。
- **MGR (MySQL Group Replication)**：基于 Paxos 协议的高可用集群解决方案，支持多主写入和自动故障转移，强一致性保障。

### 读写分离

利用中间件（如 MySQL Router, ShardingSphere 等）将写请求路由到主库，读请求分发到从库，大幅提升系统吞吐量。

## 5. 高可用与故障切换

- **MHA (Master High Availability)**：开源的故障切换工具。当主库故障时，能自动从备库中选出一个数据最新的提升为主库，并重新配置其他从库。
- **Orchestrator**：现代且强大的复制拓扑管理和高可用解决方案，提供可视化界面和更智能的故障检测机制。

## 6. 分库分表

当单表数据量千万级，且索引优化和硬件升级都达到瓶颈时，需要考虑分库分表。

- **垂直拆分**：按业务模块将不同的表拆分到不同的数据库（如用户库、订单库），或者将一张宽表拆成基础表和扩展表。
- **水平拆分 (Sharding)**：将一张表的数据按照某种规则切分到多张表或多个库中。
  - **切分策略**：Range（按时间或 ID 范围，容易产生热点数据）或 Hash（如 `user_id % 16`，分布均匀）。
- **中间件生态**：引入 ShardingSphere-JDBC 或 MyCat，使应用层对分库分表透明，仍像操作单库一样写 SQL。

## 7. 配置调优

通过修改 `my.cnf` 提升硬件利用率：

- `innodb_buffer_pool_size`：最关键的参数，通常设置为服务器可用内存的 60%-80%。
- `innodb_log_file_size`：Redo Log 大小，设置大些可减少磁盘 I/O 刷盘频率，但会增加崩溃恢复时间。
- `max_connections`：最大并发连接数，根据应用需求和服务器配置合理设置（一般 1000~3000）。
- `tmp_table_size` 和 `max_heap_table_size`：限制内存临时表的大小，超过后会转换为磁盘临时表，导致性能急剧下降，可适度调大。
